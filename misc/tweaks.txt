🔴 Critical 1 — A0 is not actually implemented as the paper says

Your paper/config says:

A0 = fixed, non-R-centered 360-sample windows, stride 256.

But train_ablation.py always calls:

build_partition(..., qtdb_record, ...)

and qtdb_record() always does:

r_peaks = pan_tompkins_r_peaks(...)
return create_windows(ecg, labels, r_peaks, post)

So A0 is also R-peak-centered.

There is currently no fixed sliding-window implementation anywhere in src/.

Even more strongly, your committed metadata says:

A0 expected: fixed windows
actual 360-sample QTDB train windows: 87,111
A1: 87,111

That is a major red flag.

Consequence

The current repository does not reproduce the A0→A1 ablation described in the paper.

This is the most important thing to fix.

🔴 Critical 2 — A4 does NOT load the A3 checkpoint

Your paper says:

A4 uses the corresponding best A3 checkpoint for each seed as initialization.

Your configs/A4.yaml says:

base_checkpoint: A3

but train_ablation.py never reads or loads base_checkpoint.

Instead, it does:

model = model_cls().to(device)
...
train_model(...)

So A4 currently:

initializes a new model → trains from scratch on QTDB → adapts on LUDB

rather than:

load trained A3 → adapt on LUDB.

This is another major reproducibility failure.

🔴 Critical 3 — Paper says model selection = validation Macro F1, code uses validation loss

Paper:

“Model selection was based on the highest Macro F1 achieved on the QTDB validation set.”

Code:

if val_loss < best_loss:
    ...
    best_state = ...

So the repository selects:

lowest validation loss

not:

highest validation Macro F1.

And the YAML files also say:

checkpoint_selection: best_validation_loss

Therefore the paper and repository disagree on checkpoint selection.

This needs to be resolved one way or the other.

Given your current paper wording, the repository should implement best QTDB validation Macro F1.

🔴 Critical 4 — Your "three seeds" don't actually control model initialization

In train_ablation.py you do:

model = model_cls().to(device)

before calling train_model().

But the seed is set inside train_model():

set_global_seed(seed)

Therefore the model weights have already been randomly initialized before the seed is set.

So the statement that seeds 1/2/3 control:

“weight initialization and minibatch ordering”

is currently false.

The DataLoader is seeded, but the initial model weights aren't.

Fix

Seed before constructing the model.

So this is really a training sweep, not a complete reproduction pipeline.

I'd change the README wording unless you build the full pipeline.

Search shows no actual hard_threshold, R4, or decoder implementation.

So right now the repo documents R4 but doesn't reproduce it.

For a reviewer asking for reproducibility, that's a gap.

first recorded channel (MLII)

Lead II (matched to QTDB's MLII)
